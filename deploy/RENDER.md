# UNO LUCK Render staging

This is an independent staging service, not a production migration or automatic
failover. `render.yaml` uses the existing Docker image, Singapore, one 512 MB
instance and a 1 GB disk. Automatic deployment is off until import and live QA
are complete. Deploy only a commit whose three CI jobs have succeeded.

## Persistent state

- Mount: `/data/uno-luck`
- Audio/catalog: `/data/uno-luck` (`UNO_SOUND_STORAGE_DIR`)
- Coin/round SQLite: `/data/uno-luck/database/uno_luck_spin.sqlite3`
  (`UNO_SPIN_DB_PATH`)
- Application UID/GID: `10001:10001`; startup prepares the two dedicated
  directories before dropping privileges. Import files under this ownership.
- A new Render-only Sound Studio admin secret is generated by the Blueprint;
  do not reuse or print the Railway secret. Player sound settings are data, not
  this credential, and must be preserved separately.
- Same-origin requests already work with the generated Render domain. No
  wildcard origin allowance is needed.

## Import and release gates

1. Verify the Render workspace/account and GitHub repository permission.
2. Create the staging service from the Blueprint at the tested branch commit.
3. Copy the existing published sound catalog and its referenced audio into the
   new disk, preserving revisions, trims, fades, repeat/mirror and mixer. Compare
   full public manifests and audio SHA-256 hashes. Do not publish/reset the
   source catalog or add a runtime dependency on Railway for audio playback.
4. Before any player migration, obtain a transactionally consistent SQLite
   backup with `sqlite3.Connection.backup`, then run `PRAGMA integrity_check`.
   Do not copy a live database file with ordinary file copy. Coordinate a write
   freeze/final backup before cutover; two independent databases are not a
   synchronized failover setup. For new staging QA use isolated fresh guests.
5. Guest cookies are origin-bound. A new `onrender.com` origin does not inherit
   existing Railway guest sessions even when the database has been copied.
   Do not promise automatic balance continuity across those URLs.
6. Verify deployment live, HTTP 200 at `/` and `/health`, content hashes, release
   `db4a15cc4c46a324a1a8`, and the v1146 panel assets. Run browser gameplay/audio
   QA and verify the sound manifest remains unchanged.
7. Confirm a container replacement preserves an incomplete paid round and its
   idempotency key; CI's `volume_round_probe.py` exercises this on loopback only.

The Railway service and production remain untouched. Render's attached disk
requires one instance and a brief interruption during deployment. Backups must
be kept independently of that disk. Account connection, data import and live
verification must be completed before calling this staging service ready.
